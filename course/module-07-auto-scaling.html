Section 1: Auto Scaling Concept & Architecture

Elastic Scaling Service (ESS)

Elastic Scaling Service (ESS) is a fully managed cloud service that automatically adjusts elastic compute capacity to match fluctuating business demands and management policies.

Compared to traditional physical servers requiring expensive over-provisioning for peak traffic, Auto Scaling dynamically launches, configures, and releases compute resources in real time. It seamlessly synchronizes with Server Load Balancer (SLB) instances and ApsaraDB RDS access whitelists, eliminating manual operational bottlenecks while maximizing cost efficiency.

⚡ Elastic Scale-Out

Automatically provisions compute resources during traffic surges to maintain consistent application SLAs.

📉 Elastic Scale-In

Automatically releases or stops idle instances during off-peak periods, preventing cloud budget waste.

🛡️ Elastic Self-Healing

Continuously inspects instance health and automatically replaces failed or unhealthy instances without human intervention.

🧠 Intelligent Triggers

Combines CloudMonitor metrics, scheduled timers, target tracking, and AI-driven predictive scaling algorithms.

🔄 Zero-Touch Ecosystem

Automatically registers instances with SLB backend groups and manages private IP whitelists on RDS databases.

Section 2: Scaling Group

Scaling Group

A Scaling Group is a logical management container of ECS instances bound to SLB and VPC infrastructure:

  • Minimum Size (MinSize): The capacity floor. Guarantees healthy instances never drop below this value.
  • Desired Capacity: The baseline target automatically maintained during normal traffic.
  • Scale-Out as Needed: Dynamic compute buffer added automatically during load surges.
  • Maximum Size (MaxSize): The capacity ceiling. Guarantees instance count never exceeds this cost limit.
  • Zero-Touch Binding: Automatically registers ECS backends with SLB and updates RDS whitelists.
Section 2: Scaling Group

Multi-Zone vSwitch Architecture

Scaling groups span multiple vSwitches across Availability Zones (AZs) to eliminate single points of failure:

  1. Priority Strategy: Provisions in primary Zone A first. If inventory or IP addresses exhaust, automatically fails over to Zone B.
  2. Balanced Strategy (HA): Distributes ECS instances evenly across all configured zones to maximize disaster recovery tolerance.
  3. Cost-Optimized Strategy: Prioritizes zones and instance families that offer lowest compute costs or deepest spot discounts.
  • Production Standard: Always bind at least 2 or 3 vSwitches across distinct Availability Zones.
Section 2: Scaling Group

Creation & Immutable Attributes

Mandatory Creation Parameters

When provisioning a new Scaling Group, administrators define:

  • Scaling Group Name: Unique identifier within the region.
  • MinSize & MaxSize: Baseline floor and ceiling capacity limits.
  • Default Cooldown Time: Lockout duration in seconds (default: 300s).
  • Removal Policy: Rule governing which instances are evicted during scale-in.
  • Network Configuration: Target VPC and multi-zone vSwitches.
  • Load Balancer & Database: Associated SLB instances and RDS databases.

Mutable vs. Immutable Attributes

Understanding architectural boundaries after group creation:

  • Strict Immutable Attributes:
    • Region: Cannot be moved across regions once created.
    • Network Type: VPC network type cannot be switched to Classic.
    • Primary VPC ID: Cannot be rebound to a different VPC.
  • Dynamically Mutable Attributes:
    • MinSize, MaxSize, and Desired Capacity.
    • Default Cooldown period and Removal Policies.
    • Associated SLB instances and RDS database instances.
    • Associated vSwitches within the same VPC.
Section 2: Scaling Group

Scaling Group States

1. Active State

The operational state of a Scaling Group:

  • Requires at least one Active Scaling Configuration.
  • Accepts and executes scaling rules, scheduled tasks, and alarm tasks.
  • Maintains total instance count between MinSize and MaxSize.
  • Performs periodic self-healing health check replacements.

2. Inactive State

The paused management state:

  • Reject all automated scaling rule executions and trigger tasks.
  • Existing ECS instances remain running and serving traffic.
  • Allows administrative modifications to configurations and rules.
  • Can be re-enabled once an active scaling configuration is ready.

3. Deleting State

The termination teardown state:

  • Triggered via console or DeleteScalingGroup API.
  • Rejects all incoming scaling requests and activity triggers.
  • Terminates all automatically launched ECS instances.
  • Removes associated configurations, rules, and activity logs.

State Transition Constraint: A Scaling Group can only transition to Inactive when no Scaling Activity is currently in progress. Administrative updates (modifying Min/Max size, attaching SLB) can be performed in either Active or Inactive state.

Section 2: Scaling Group

Instance Removal Policies

Zone Balancing First

RemovalPolicy.1 & .2

Evaluates OldestScalingConfiguration, OldestInstance, or NewestInstance in sequence.

Graceful Deregistration

Reclaim Modes

Release Mode (Default)

Permanently terminates and deletes ECS instances. Compute and storage charges stop immediately.

Shutdown & Reclaim Mode

Stops instances without deletion (No-Fee When Stopped), enabling instantaneous warm restart.

Manual Preservation

Manually attached instances are detached from SLB/group but remain running independently.

Section 2: Scaling Group

What Happens If a Scaling Group Is Deleted

ForceDelete Execution

Deleting a Scaling Group via the console or OpenAPI:

  1. Teardown Initiation: Group enters Deleting state and halts all incoming scaling requests.
  2. Traffic Deregistration: Automatically detaches all instances from associated SLB backends and removes IPs from RDS whitelists.
  3. Instance Termination: In ForceDelete mode, Auto Scaling automatically terminates all automatically launched ECS instances.
  4. Manual Instance Detachment: Manually added instances are safely detached and remain untouched in the user account.

Resource Deletion Scope

Understanding which assets are removed vs. preserved:

  • Permanently Deleted:
    • The Scaling Group container itself.
    • All internal Scaling Configurations and Scaling Rules.
    • All Scaling Activities and execution history logs.
  • Preserved & Untouched:
    • Associated Server Load Balancer (SLB) instances.
    • Associated ApsaraDB RDS database instances.
    • Independent Scheduled Tasks and CloudMonitor alarms.
    • Virtual Private Cloud (VPC) and vSwitches.
Section 3: Scaling Configuration (Templates)

Scaling Configuration

A Scaling Configuration serves as the technical blueprint defining the hardware and software specifications of ECS instances provisioned by Auto Scaling:

  • Compute Specification: Instance Type / Family (e.g. ecs.g7.xlarge, 4 vCPU, 16 GiB memory).
  • Operating System Image: Public image, Custom image (golden AMI), or Alibaba Cloud Marketplace image.
  • Storage Tiers: System disk category (ESSD PL0–PL3) and capacity; optional data disk attachments.
  • Network & Security: Security Group IDs, public IPv6 dual-stack, or EIP bandwidth allocations.
  • Credentials & Access: SSH Key Pair, password, or RAM Role for instance authentication.
  • User Data Script: Cloud-init shell script for automated boot-time software initialization and package updates.

Architectural Best Practices:

  • Pre-Baked Custom Images: Package application binaries, dependencies, and system configurations directly into a golden image to minimize boot-up time during scale-out events.
  • Instance RAM Roles: Assign an instance RAM role in the scaling configuration rather than embedding hardcoded AccessKey credentials in User Data scripts.
  • ESSD Storage Tiering: Choose ESSD AutoPL or PL1 system disks to ensure sufficient IOPS during application startup without storage throughput bottlenecks.
Section 3: Scaling Configuration (Templates)

Scaling Configuration States

Active Configuration

The single operational blueprint:

  • A Scaling Group can have only ONE Active Scaling Configuration at any given time.
  • All newly triggered scale-out activities use this active configuration to launch instances.
  • Cannot be deleted while marked as Active.

Inactive Configurations

Alternative blueprints:

  • A Scaling Group can store up to 10 Scaling Configurations simultaneously.
  • Allows staging newer instance generations or updated software images without downtime.
  • Can be switched to Active instantly with zero service disruption.

Deletion Rules

Strict safety constraints:

  • Active configurations cannot be deleted directly; must switch to another configuration first.
  • A configuration cannot be deleted if running instances created by that configuration still exist in the group.

Immutable Modification Principle: Once created, individual attributes of a Scaling Configuration cannot be edited in place. To update instance specs or image IDs, administrators create a new Scaling Configuration and set it as Active.

Section 3: Scaling Configuration (Templates)

Multi-Family Specifications & Spot Pooling

Multi-Instance Type Configuration

Preventing inventory stockouts in high-density regions:

  • Administrators can configure up to 10 instance types in priority order within a single scaling configuration.
  • During scale-out, Auto Scaling attempts to provision the first priority instance family (e.g. ecs.c7.large).
  • If inventory is exhausted in that zone, it seamlessly falls back to subsequent configured families (e.g. ecs.c6.large, ecs.g7.large).

Spot Instance Diversification

Maximizing compute capacity at fraction of cost:

  • Combine Pay-As-You-Go with Spot instances to achieve up to 80% to 90% cost savings.
  • Configure Spot allocation strategy: Cost-Optimized (selects lowest price) or Capacity-Optimized (selects lowest eviction probability).
  • Automated On-Demand Fallback: If Spot instances are unavailable or reclaimed, Auto Scaling automatically provisions Pay-As-You-Go instances to preserve capacity.
Section 3: Scaling Configuration (Templates)

ECS Launch Templates Integration

Decoupled Launch Templates

Modern cloud architecture replaces static scaling configurations with global ECS Launch Templates:

  • Reusable Blueprints: A single Launch Template can be shared across multiple Scaling Groups, E-MapReduce clusters, and manual ECS provisioning.
  • Unified Governance: Centralizes instance specification governance, AMI updates, and security compliance.
  • Multi-Version Management: Launch Templates maintain full version history (Version 1, Version 2, Version 3).

Version Binding in Auto Scaling

Flexible version binding options for Scaling Groups:

  • Specific Version Pinning: Pin the Scaling Group to a tested version (e.g. Version 2) to guarantee operational consistency across deployments.
  • Default Version Tracking: Automatically tracks the template's designated Default Version, enabling instant canary rollouts.
  • Latest Version Tracking: Automatically adopts the latest published template version whenever a new scale-out activity occurs.
Section 4: Scaling Rules

Scaling Rules Fundamentals

A Scaling Rule defines the specific quantitative action executed when a scaling event is triggered:

  • Action Types:
    • Add $N$ Instances: Increases capacity by a fixed count (e.g., Add 2 instances).
    • Remove $N$ Instances: Decreases capacity by a fixed count (e.g., Remove 1 instance).
    • Adjust to $N$ Instances: Sets absolute total capacity to a specific number (e.g., Adjust to 10 instances).
    • Percentage Scaling: Adjusts capacity by a percentage of current total (e.g., Add 25%).
  • Rule Types: Simple Scaling Rule, Target Tracking Scaling Rule, and Step Scaling Rule.
  • Cooldown Parameter: Optional rule-specific cooldown time that overrides the group's default cooldown.

Rule Execution Behavior:

  • Direct Execution: Manually triggering a scaling rule executes immediately without waiting for cooldown expiration.
  • Alarm Association: Rules are linked to CloudMonitor alert tasks or scheduled tasks to automate execution.
  • Activity Generation: Every successful rule execution generates a tracked Scaling Activity recording instance IDs, timings, and outcomes.
Section 4: Scaling Rules

Strict Boundary Clamping

MaxSize Ceiling Clamping

Scaling rules can never breach the group's upper boundary:

  • Scenario: Scaling Group MaxSize = 3, Total Capacity = 2. A rule triggers to "Add 3 instances".
  • Outcome: Auto Scaling clamps the request and adds only 1 instance, bringing total capacity exactly to MaxSize (3).

MinSize Floor Clamping

Scaling rules can never breach the group's lower boundary:

  • Scenario: Scaling Group MinSize = 2, Total Capacity = 3. A rule triggers to "Remove 5 instances".
  • Outcome: Auto Scaling clamps the request and removes only 1 instance, preserving the MinSize baseline (2).
Section 4: Scaling Rules

Target Tracking Scaling

Autonomous Capacity Calculation

Target Tracking eliminates the need for manual metric thresholds and complex step rules:

  • Set a Target Metric: The administrator specifies a desired target value (e.g. maintain Average CPU Utilization at 50%).
  • Continuous Closed-Loop Control: Auto Scaling continuously monitors telemetry and automatically calculates the exact number of instances to add or remove to keep the metric near target.
  • Proportional Response: Automatically handles small drifts with minor adjustments and large traffic surges with massive instant scale-out.

Supported Predefined Metrics

Built-in CloudMonitor telemetry integrations:

  • CpuUtilization: Average CPU usage across all instances in the group (e.g., target: 60%).
  • ClassicInternetRx: Average inbound network traffic rate per instance.
  • ClassicInternetTx: Average outbound network traffic rate per instance.
  • IntranetRx / IntranetTx: Internal VPC intranet traffic flows.
  • SLB Request Count: Number of incoming HTTP/HTTPS requests per target server.
Section 4: Scaling Rules

Step Scaling Rules

Graduated Threshold Architecture

Step Scaling provides tiered responses based on the severity of a metric alarm breach:

  • Different scaling adjustments are applied depending on how far the metric exceeds the alarm threshold.
  • Provides aggressive instant capacity expansion during massive surges while preventing over-scaling during modest traffic bumps.
  • Continues responding to changing metric values even during active execution steps.

Concrete Step Scaling Example

Baseline alarm configured at CPU Utilization > 60%:

  • Step 1 (60% to 70% CPU): Add 1 instance (gentle drift mitigation).
  • Step 2 (70% to 85% CPU): Add 4 instances (moderate load surge).
  • Step 3 (> 85% CPU): Add 10 instances (emergency flash sale spike).

Warm-Up Optimization: Instances launched via step scaling observe an instance warm-up timer before their metrics are included in cluster averages.

Section 5: Trigger Mechanisms & Scheduling

Auto Scaling Operational Usage Workflow

The standard 6-step lifecycle for deploying and automating Auto Scaling:

  1. Create Scaling Group: Configure MinSize, MaxSize, default cooldown, VPC network, SLB, and RDS instances.
  2. Create Scaling Configuration: Define ECS instance attributes such as Image ID, instance family, and security groups.
  3. Enable Scaling Group: Activate the scaling group with the scaling configuration created in Step 2.
  4. Create Scaling Rules: Define specific scaling actions, such as adding or removing $N$ instances.
  5. Create Scheduled Tasks: Trigger scaling rules at specific planned times (e.g. scale up at 12:00 AM daily).
  6. Create Alarm Tasks: Configure CloudMonitor rules to dynamically scale based on real-time metrics (e.g. CPU ≥ 80%).
Section 5: Trigger Mechanisms & Scheduling

Direct Execution & Manual Operations

Direct Rule Execution

Manual administrative triggers via console or API:

  • Can be executed whenever the group is in Active state and no activity is currently running.
  • Cooldown Bypass: Direct manual execution bypasses the cool-down time and executes immediately.
  • Respects Min/Max boundaries: If added instances would exceed MaxSize, the operation is clamped to MaxSize.

Attaching & Detaching Running Instances

Integrating pre-existing ECS instances:

  • Adding Existing Instances: Existing instances in the same VPC/region can be attached to the group. The operation fails immediately if adding them exceeds MaxSize.
  • Configuration Independence: Manually attached instances are NOT tied to the active Scaling Configuration.
  • Detaching Instances: Detached instances are removed from SLB/RDS, but are NEVER stopped or deleted.
Section 5: Trigger Mechanisms & Scheduling

Scheduled Tasks & Recurring Cron

Scheduled Task Architecture

Predictable traffic scheduling for planned events:

  • Create up to 20 scheduled tasks per scaling group.
  • Triggers a specific Scaling Rule at a designated launch time (e.g. 13:00 every weekday).
  • Supports flexible recurrence patterns: Daily, Weekly, Monthly, or standard Cron expressions.
  • Cooldown Bypass: Scheduled tasks can execute immediately without waiting for cool-down expiration.

Launch Expiration Window

Preventing task abandonment during busy activities:

  • Launch Expiration Time: Configurable retry window (default: 600s, up to 86,400s).
  • If a scheduled task triggers while the group is busy executing another activity, the task retries automatically within the expiration window.
  • Once the active activity completes and the group becomes idle, the scheduled task executes immediately.
  • If the window expires before execution, the task is safely abandoned.
Section 5: Trigger Mechanisms & Scheduling

Scheduled Task Concurrency Resolution

Concurrency Execution Rules

Strict order resolution when multiple scheduled tasks conflict:

  • Single Activity Invariant: A Scaling Group can execute only ONE Scaling Activity at a time. Simultaneous activities are strictly prohibited.
  • Earliest Task Priority: If multiple tasks trigger at overlapping times, the earliest scheduled task triggers its activity first. Remaining tasks retry within their Launch Expiration Times.
  • Simultaneous Conflict Resolution: If multiple tasks are scheduled at the exact same second, Auto Scaling executes the latest created task and abandons earlier conflicting tasks.

Conflict Flow Resolution

  1. Task 1 Triggers (10:00:00): Scaling Activity 1 starts adding 5 instances (takes 180s).
  2. Task 2 Triggers (10:01:00): Blocked because Activity 1 is active; enters Launch Expiration retry loop.
  3. Activity 1 Completes (10:03:00): Task 2 successfully executes its rule within its expiration window.
Section 5: Trigger Mechanisms & Scheduling

CloudMonitor Metric Alarm Tasks

Telemetry Alarm Architecture

Dynamic scaling triggered by real-time infrastructure metrics:

  • Monitors telemetry streams collected by the CloudMonitor agent on each ECS instance.
  • Statistical Functions: Evaluates Average, Maximum, or Minimum across all instances in the Scaling Group.
  • Evaluation Periods: Configures continuous evaluation periods (e.g. 3 consecutive checks of 1 minute) to filter out transient metric spikes.
  • Comparison Operators: Triggers linked Scaling Rules when metric ≥ or ≤ threshold.

Core Telemetry Metrics

Key metrics used in enterprise scaling alarms:

  • CpuUtilization: Processor load (scale-out at ≥ 75%, scale-in at ≤ 25%).
  • MemoryUtilization: Memory saturation for caching tiers.
  • IntranetIn / IntranetOut: Internal bandwidth flows across application tiers.
  • TcpConnection: Active socket counts on web application servers.
  • SystemDiskReadBps / WriteBps: Storage I/O throughput bottlenecks.
Section 5: Trigger Mechanisms & Scheduling

Cool-Down Period Architecture

The Cool-Down Mechanics

Preventing flapping and over-provisioning cycles:

  • Lockout Window: A configurable period (default: 300 seconds, 0–86,400s) during which the scaling group stabilizes.
  • Start Timestamp: The cool-down timer begins immediately after the last ECS instance is successfully added or removed by a Scaling Activity.
  • Purpose: Allows newly launched instances to complete OS boot-up, start application services, warm up memory caches, and absorb traffic before metrics are re-evaluated.

The Asymmetric Lockout Rule

Crucial distinction between trigger types during cooldown:

  • REJECTED During Cooldown: Scaling activities requested by CloudMonitor alarm tasks are strictly rejected to prevent runaway over-scaling.
  • ALLOWED During Cooldown: Manually executed scaling rules and Scheduled Tasks bypass cooldown and execute immediately.
  • Architectural Value: Ensures operational emergency overrides can always execute while preventing autonomous telemetry feedback loops.
Section 5: Trigger Mechanisms & Scheduling

Scaling Activity Atomicity & Rollback Integrity

Atomicity & Non-Interruptible Invariant

Scaling Activity execution characteristics:

  • Single Activity Execution: Only one scaling activity can execute in a Scaling Group at any point in time.
  • Non-Interruptible: Once initiated, an activity cannot be paused, stopped, or forcibly aborted. For example, if adding 20 instances, it cannot be terminated halfway after creating 5.

Instance-Level Rollback Integrity

How Auto Scaling handles partial operational failures:

  • System Rollback Target: When an activity fails to complete (e.g. 20 instances created, but 1 fails to attach to SLB), the system maintains instance integrity, NOT activity integrity.
  • Targeted Release: The system releases only the failed instance; successfully configured instances remain active in the group.
  • Billing Implication: Because Auto Scaling provisions instances via the ECS API, rolled-back instances incur standard Pay-As-You-Go charges for the brief period they ran.
Section 6: Lifecycle Hooks & Event Notifications

Lifecycle Hooks Architecture

PENDING_ADD (Scale-Out Hook)

Suspends newly launched instances before traffic arrives:

  • Instance is created, disks attached, and IP assigned.
  • Hook suspends the instance in PENDING:WAIT state before it is added to SLB backends or RDS whitelists.
  • Enables custom package installation, schema initialization, and cache pre-warming via Cloud Assistant.

PENDING_REMOVE (Scale-In Hook)

Suspends instances during scale-in before VM destruction:

  • Instance is removed from SLB backends; traffic drains safely.
  • Hook suspends the instance in PENDING:WAIT state before deletion.
  • Allows uploading local log files to OSS, saving memory states, and finishing background queue tasks with zero loss.
Section 6: Lifecycle Hooks & Event Notifications

Lifecycle Hook Pipeline & Heartbeats

1. Timeout Window

Configurable timeout (30 to 21,600s, default 600s). If script finishes early, it sends CompleteLifecycleAction immediately.

2. Heartbeat Extension

Long operations can invoke RecordLifecycleAction to extend the timeout, resetting the countdown clock.

3. Hook Outcomes

CONTINUE proceeds to IN_SERVICE or termination. ABANDON aborts scale-out, releasing the instance cleanly.

Section 6: Lifecycle Hooks & Event Notifications

Graceful Scale-In Evacuation

The In-Flight Data Loss Dilemma

Abruptly terminating web servers during scale-in causes sever customer-facing errors:

  • Active HTTP sessions and long-polling connections are severed mid-transaction, generating HTTP 502/504 errors.
  • Local application transaction logs stored on ephemeral system disks are destroyed before being archived to central storage.
  • Asynchronous queue workers processing payment or report jobs are terminated without completing state checkpoints.

The 4-Step Graceful Evacuation Architecture

  1. SLB Connection Draining: Instance weight is set to 0. SLB stops routing new connections while allowing existing requests up to 300 seconds to complete cleanly.
  2. Trigger PENDING_REMOVE Hook: Auto Scaling suspends VM deletion and triggers a Cloud Assistant notification.
  3. Automated Log & Queue Flushing: Local shell scripts upload application logs to Object Storage Service (OSS) and finish pending jobs.
  4. Signal CompleteLifecycleAction: Cloud Assistant signals Auto Scaling to release the VM with zero customer impact.

Section 7: Cloud-Native Scaling & Cost Optimization

Serverless Container Bursts with ECI

Modern cloud architecture combines ECS virtual machines with Elastic Container Instance (ECI) for hybrid scaling:

  • Baseline Capacity on ECS: Run steady-state base traffic on Reserved/Subscription ECS instances for maximum predictable cost efficiency.
  • Instant Burst to ECI: During sudden extreme surges, Auto Scaling provisions serverless ECI container pods in under 10 seconds without waiting for full VM boot times.
  • Zero Server Management: ECI pods run serverless sandboxes without underlying host OS management or cluster capacity constraints.
  • Kubernetes Integration: Seamlessly coordinates with Container Service for Kubernetes (ACK) via virtual-kubelet to absorb traffic bursts.

Predictive Scaling & AI Forecasting

The Cold-Start Latency Challenge

Traditional reactive scaling responds only AFTER metrics breach alarms:

  • Metric evaluation takes 1 to 3 minutes; VM provisioning, OS boot, and application startup require an additional 3 to 5 minutes.
  • During this 5–8 minute cold-start window, user requests experience elevated latency, degraded performance, or timeouts.

AI-Driven Predictive Forecasting

Auto Scaling incorporates machine learning time-series models:

  • Historical Pattern Analysis: Analyzes metric history (CPU, memory, traffic) over the past 24 hours to 14 days to identify recurring cyclical patterns.
  • 24-Hour Horizon Plan: Generates predictive scaling schedules 24 hours in advance, forecasting required capacity for every hour.
  • Proactive Capacity Warming: Provisions and warms instances minutes BEFORE demand actually surges, completely eliminating reactive cold-start latency.

Zero-Touch Security & Whitelisting

SLB Backend Auto-Binding

Automating traffic ingestion security:

  • Automatically registers newly launched instances into default or VServer backend groups of associated SLB/ALB instances.
  • Inherits health check settings and listener forwarding rules automatically.
  • Supports weighted traffic distribution and graceful connection draining during scale-in.

ApsaraDB RDS Auto-Whitelisting

Eliminating manual database security overhead:

  • Automatically appends the VPC private IP address of each new instance to the security IP whitelist of associated RDS databases.
  • Applications immediately establish database connections upon boot without connection rejection errors.
  • Automatic Pruning: Removes terminated instance IPs immediately during scale-in, preventing unauthorized reuse or IP leakage.

Auto Scaling Pricing & Cost Optimization

100% Free Service Orchestration

Auto Scaling management capabilities are completely free of charge:

  • Zero subscription fees for Scaling Groups, Configurations, Rules, or Activities.
  • Zero fees for CloudMonitor integration or health check inspection.
  • Billed Only for Underlying Compute: You pay exclusively for standard ECS instances, ECI container pods, cloud disks, and network bandwidth actually provisioned.

The 3-Tier Enterprise Cost Optimization Model

  1. Baseline Capacity (Savings Plans): Cover minimum predictable baseline instances with Savings Plans or Reserved Instances (up to 50–70% savings).
  2. Dynamic Daytime Surges (Pay-As-You-Go): Scale variable daytime demand using standard Pay-As-You-Go compute, paying per-second only when running.
  3. Fault-Tolerant Batch Bursts (Spot Instances): Use Spot instances for non-critical, queue-based, or container workloads (up to 80–90% savings).

Target Tracking dynamically aligns capacity with traffic surges, multi-zone vSwitches eliminate single-zone inventory risks, SLB connection draining protects in-flight transactions during scale-in, and RDS auto-whitelisting guarantees instant database connectivity.
✖ Option C is Incorrect
Single-zone deployment introduces severe single-point-of-failure risks and inventory bottlenecks, while a 0-second cooldown causes continuous metric instability and rapid instance flapping.

Auto Scaling scales horizontally by adding/removing instances rather than upgrading instance specifications vertically in place; vertical resizing incurs downtime and cannot scale dynamically across multiple zones.

Scenario 3: Solution & Architectural Analysis

Correct Answer: A Lifecycle Hook PENDING_REMOVE + Cloud Assistant State Evacuation + OSS Upload
Validated Architecture
✔ Option A is Correct
The PENDING_REMOVE lifecycle hook pauses instance destruction while SLB connection draining completes active HTTP sessions; Cloud Assistant safely archives transaction logs to OSS and signals completion with zero transaction loss.
✖ Option B is Incorrect
Immediate release without hooks abruptly terminates running checkout sessions, generating HTTP 502/504 errors and permanently destroying un-archived audit logs on the local system disk.

✖ Option D is Incorrect
SMS alerts are asynchronous notifications and cannot pause or intercept the automated scale-in activity, meaning instances would terminate long before human operators could respond.
